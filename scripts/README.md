# Scripts

Scripts run by hand for testing and operations, such as deploys, DAO setup and checks against live services (ADR 0005).

- `test.sh`: runs the NEAR sandbox tests, the Foundry tests and the Vite+ checks and tests. Run it from anywhere: `./scripts/test.sh`.
- `check-near-ai-signing.mts`: sends one AI Verdict request to NEAR AI Cloud and checks that the response carries a `provider_tee` ed25519 signature over the exact request and response bytes, from the key in the model's attestation report. It needs `NEARAI_API_KEY` and costs well under $0.001 per run. Run it from the repository root:

  ```bash
  node --env-file-if-exists=.env scripts/check-near-ai-signing.mts                  # check Prompt Template v1's model
  node --env-file-if-exists=.env scripts/check-near-ai-signing.mts --model <id>     # try another model with the same settings
  node --env-file-if-exists=.env scripts/check-near-ai-signing.mts --write-fixture  # also replace fixtures/near-ai-cloud/signed-response.json
  ```

  It exits non-zero if any check fails. Results are in `docs/research/near-ai-cloud.md` §7.
- `storage-upload.sh <file>`: uploads a Claim or Evidence file to the storage service and prints its sha256 hash, the value to record on-chain. Status messages go to standard error, so `hash=$(./scripts/storage-upload.sh claim.txt)` works.
- `storage-download.sh <hash> [output]`: downloads content by hash, checks that its sha256 matches, and writes it to `output` or standard output. It writes nothing if the bytes don't match.
- `deploy-storage.sh [testnet|mainnet]`: deploys the storage service with Cloudflare credentials from the environment or the root `.env`.
- `deploy-keeper.sh [testnet|mainnet]`: deploys the Keeper (`typescript/apps/keeper`) as the Worker `enzure-keeper` with its secrets; its cron trigger starts the alarm loop within a minute. Needs `ORACLE_ACCOUNT_ID`, `NEAR_ACCOUNT_ID`, `STORAGE_URL`, `NEAR_PRIVATE_KEY` and `NEARAI_API_KEY`, plus `<CHAIN>_RPC_URL` and `<CHAIN>_RELAYER_KEY` for each Relayer chain (`BASE_RPC_URL`, `BASE_RELAYER_KEY`), and the same Cloudflare credentials as `deploy-storage.sh`. Secrets go to `cf deploy --secrets-file` in a temporary file, never on a command line. `--dry-run` builds and checks without uploading.
- `deploy-web.sh [testnet|mainnet]`: builds and deploys the web app (`typescript/apps/web`) as the Worker `enzure-web`. Needs `ORACLE_ACCOUNT_ID` and `STORAGE_URL` (build-time config) and the same Cloudflare credentials as `deploy-storage.sh`.

The deploy scripts take the network as an optional first argument, `testnet` by default, and pass it to `cf deploy --mode`. Each app's `cloudflare.config.ts` returns that network's Worker: testnet keeps the names above, and mainnet adds `-mainnet` (`enzure-storage-mainnet` with the R2 bucket `enzure-content-mainnet`, `enzure-web-mainnet`, `enzure-keeper-mainnet`). Values come from the environment first, then the network's env files in the repository root (`scripts/lib/env.sh`): `.env.testnet` then `.env` for testnet, and only `.env.mainnet` for mainnet, which falls back to `.env` for `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` alone. A `NEAR_NETWORK` that names the other network stops the deploy. Other arguments go to `cf deploy`, so `./scripts/deploy-keeper.sh mainnet --dry-run` checks a mainnet deploy without uploading.
- `oracle-undisputed.sh`: runs the undisputed path on NEAR testnet. It builds the oracle, deploys it to a new development account `oracle-<timestamp>.<NEAR_ACCOUNT_ID>`, posts an Assertion with a 60-second Liveness, settles it once Liveness ends, withdraws the bond, and prints a NearBlocks link for each transaction. It takes `NEAR_ACCOUNT_ID` and `NEAR_PRIVATE_KEY` from the environment or the root `.env`, and needs about 3.1 testnet NEAR: 2 NEAR stays on the development account (delete it to recover it) and the 1 NEAR bond comes back. Optional: `ORACLE_DAO_ACCOUNT_ID`, `LIVENESS_SECS`, `BOND_YOCTO`, `ORACLE_BALANCE`.
- `oracle-evm-hook.sh [--write-fixture]`: signs one EVM Hook through Chain Signatures on NEAR testnet. Like `oracle-undisputed.sh`, it deploys the oracle to a new development account, then posts an Assertion with one EVM Hook, settles it, calls `sign_hook` on `v1.signer-prod.testnet`, prints the signed result and the oracle's derived EVM address, and withdraws the bond. `--write-fixture` replaces `fixtures/chain-signatures/signed-result.json`. Same credentials as `oracle-undisputed.sh`; about 4.1 testnet NEAR, of which 3 NEAR stays on the development account. Optional: `ORACLE_ACCOUNT_ID` (reuse a deployed oracle instead of deploying one; then it needs only the bond and fees), `EVM_SIGNER`, `EVM_CHAIN_ID`, `EVM_RECEIVER`, `EVM_CONSUMER`, `SIGN_DEPOSIT`, `LIVENESS_SECS`, `BOND_YOCTO`, `ORACLE_BALANCE`, `ORACLE_DAO_ACCOUNT_ID`.
- `deploy-receiver.sh <oracle-account-id> [--with-example-consumer]`: deploys the Receiver for that oracle to Base Sepolia and records it in `contracts/evm/deployments/<chain id>.json`. It reads the oracle's derived EVM address with `oracle-evm-address.mts` (or takes `ORACLE_EVM_ADDRESS`) and runs `contracts/evm/script/DeployReceiver.s.sol`. `--with-example-consumer` also deploys `examples/evm-consumer` for the new Receiver. It needs `EVM_PRIVATE_KEY`, a deployer key with Base Sepolia ETH, from the environment or the root `.env`; optional `EVM_RPC_URL` (`https://sepolia.base.org`) and `NEAR_RPC_URL`. The key reaches forge through the environment, never the command line.
- `relay-evm-hooks.mts <oracle-account-id>`: one Relayer pass. It reads the oracle's Assertions and delivers every signed EVM Hook for the chain at `EVM_RPC_URL` to its Receiver, skipping results already recorded, and prints a Basescan link per delivery. The Keeper runs the same core function, `relayOnce`, on every pass, once per Relayer chain. Needs `EVM_PRIVATE_KEY` (pays the gas): `node --env-file-if-exists=.env scripts/relay-evm-hooks.mts <oracle-account-id>`.
- `keeper-dispute.sh`: runs a dispute on NEAR testnet with the Keeper doing the resolving. It deploys a development oracle, makes `NEAR_ACCOUNT_ID` its DAO (Appeal Window 60 s, Prompt Template v1, the model's attested key as a Registered Key, checked with `near-ai-attested-key.mts`), uploads the Claim and both Evidence items from `fixtures/near-ai-cloud/` to storage, posts and disputes an Assertion, then starts the built Keeper (`typescript/apps/keeper`) and waits until it has submitted the AI Verdict and settled the Assertion. Prints every transaction link, the Keeper's included. Needs `NEAR_ACCOUNT_ID`, `NEAR_PRIVATE_KEY` and `NEARAI_API_KEY`, and about 7 testnet NEAR (4 NEAR stays on the development account). `NO_KEEPER=1` waits for a Keeper already running on that oracle (such as the deployed Worker with `ORACLE_ACCOUNT_ID` set to it) instead; `ORACLE_ACCOUNT_ID` reuses an oracle this script set up.
- `oracle-evm-address.mts <oracle-account-id> [--rpc <url>]`: prints the EVM address a deployed oracle signs EVM Hooks with. It reads the signer, path and domain from the oracle's `get_evm_signer` view and asks the signer for `derived_public_key`. Needs no credentials: `node scripts/oracle-evm-address.mts oracle.testnet`.

### DAO governance (ADR 0004)

The oracle's DAO is a Sputnik DAO v2 created through the testnet factory `sputnikv2.testnet` (`sputnik-dao.testnet` has no contract). Every DAO script signs as `NEAR_ACCOUNT_ID` with `NEAR_PRIVATE_KEY`, taken from the environment or the root `.env`; for the proposal and vote scripts that is a council member. Council keys are never committed and never passed on a command line.

- `dao-setup.sh`: creates the DAO `<DAO_NAME>.sputnikv2.testnet` with one `council` role (members from `COUNCIL`, comma separated, default `NEAR_ACCOUNT_ID`) that can propose, vote and finalize; a proposal passes on `APPROVALS` council votes (default 1, so the demo council approves quickly). The proposal bond is 0.1 NEAR and comes back when a proposal passes. It then builds the oracle and deploys it to a new account `oracle-<timestamp>.<NEAR_ACCOUNT_ID>` (or `ORACLE_ACCOUNT_ID`) with the DAO as its DAO account and treasury. About 9.6 testnet NEAR: 6 for the DAO account, 3.5 for the oracle account.
- `dao-propose.sh <dao> <oracle> <kind> ...`: files a DAO proposal calling one of the oracle's DAO-only methods, each with one yoctoNEAR. Kinds: `register-key [model]` (first runs and prints the off-chain attestation check, `near-ai-attested-key.mts`, and proposes the attested key only if it passes; needs `NEARAI_API_KEY`), `remove-key <hex>`, `publish-template [file]` (default: the template in `fixtures/near-ai-cloud`), `set-config '<JSON fields to change>'`, `resolve-appeal <assertion id> <true|false>`, `upgrade [wasm]` (builds the oracle if no file is given; the proposal names the code's sha256). `APPROVE=1` also votes for it as the proposer and prints the oracle view that shows the change. It refuses an oracle whose DAO is a different account.
- `dao-approve.sh <dao> <proposal id>`: prints the proposal (for `upgrade`, the code's size and sha256 instead of the bytes), votes for it, and prints the events the oracle logged. Exits non-zero if the approved call failed.
- `dao-appeal.sh <dao> <oracle>`: posts an Assertion, disputes it from a new account `disputer-<timestamp>.<NEAR_ACCOUNT_ID>`, waits out the AI Verdict deadline, calls `check_timeout`, rules it through a `resolve_appeal` proposal (`RULING`, default `true`), prints the oracle balances that show the bond split and withdraws the winner's. Set a short `ai_verdict_deadline` first. About 2.3 testnet NEAR with a 1 NEAR bond; 1.5 comes back.
- `near-ai-attested-key.mts [--model <id>]`: the off-chain attestation check behind `register-key`. It fetches the model's attestation report with a fresh nonce, checks there is exactly one ed25519 attestation for the model, that it echoes the nonce and that its TDX quote's report data binds the key to that nonce, and prints the key. It does not verify Intel's signature over the quote.
- `oracle-lockdown.sh <oracle> [--verify-only]`: deletes every full-access key of the named oracle account in one transaction, then checks none remain. It refuses unless that account holds an Enzure oracle whose DAO is a Sputnik DAO, and, if `NEAR_ACCOUNT_ID` is set, unless it equals the named account. `NEAR_PRIVATE_KEY` must be one of the oracle's full-access keys. `--verify-only` needs no keys and is how anyone checks the deployment.

### EVM Hook end to end on testnet

1. `./scripts/oracle-evm-hook.sh` deploys a development oracle (its first Hook goes to placeholder addresses) and prints the oracle account.
2. `./scripts/deploy-receiver.sh <oracle> --with-example-consumer` deploys a Receiver for that oracle's derived address and the example Consumer.
3. `ORACLE_ACCOUNT_ID=<oracle> EVM_RECEIVER=<receiver> EVM_CONSUMER=<consumer> ./scripts/oracle-evm-hook.sh` posts, settles and signs an Assertion with a Hook to them.
4. `node --env-file-if-exists=.env scripts/relay-evm-hooks.mts <oracle>` delivers it; `cast call <consumer> "results(uint256)(bool,bool,bytes32,bytes32)" <assertion id> --rpc-url https://sepolia.base.org` shows the recorded outcome.

The storage scripts use `STORAGE_URL`, which defaults to the deployed service at `https://enzure-storage.luckzivanius.workers.dev`.

The NEAR scripts write the private key to an access-key file in a temporary folder only they can read, and delete it on exit, so the key never appears in a command line.
